# QGramm

Self-hosted ядро обмена сообщениями на Go для чатов поддержки, общения пользователей и защищенных AI-каналов. Контейнер предоставляет API и доставку; интерфейс, регистрацию и клиентскую реализацию шифрования создает интегратор.

Исходное Swift-приложение сохранено в ветке `messenger`. Разработка нового ядра идет в `dev`; история Git сохранена. Лицензия — Apache-2.0.

## Зачем QGramm?

QGramm подходит, когда у приложения уже есть пользователи и интерфейс, а нужны устойчивые чаты, права устройств, шифрование и опциональные AI-получатели в одном сервисе. Неиспользуемые функции исключаются из сборки. В первом релизе нет федерации и горизонтального кластера; клиент реализует криптографию и WebRTC. Это предварительная версия, без заявления о превосходстве в безопасности или зрелости.

| Проект | Основное назначение | Хранение и развертывание | Шифрование | Что остается приложению |
|---|---|---|---|---|
| **QGramm** | Встраиваемые чаты поддержки, пользователей и AI | Go-контейнер; SQLite и volume файлов | HPKE до контейнера; опциональный MLS E2EE с [public member commits](docs/e2ee.ru.md) | Идентификация, UI, клиентская криптография и медиа; внешний TURN |
| [Matrix / Synapse](https://element-hq.github.io/synapse/latest/setup/installation.html) | Федеративный обмен сообщениями, экосистема клиентов | Homeserver; для production рекомендуется PostgreSQL; медиахранилище | Клиентский [Olm/Megolm E2EE](https://spec.matrix.org/v1.18/olm-megolm/) | Интеграция клиента, развертывание и медиасервисы по необходимости |
| [Centrifugo](https://centrifugal.dev/docs/server/history_and_recovery) | Транспорт real-time pub/sub | Go-сервер; память или внешний broker; ограниченный кеш восстановления | Шифрование payload реализует приложение | Постоянная БД чатов, ACL, вложения, звонки и AI |
| [Zulip](https://github.com/zulip/zulip/blob/main/docs/production/deployment.md) | Готовый командный чат с темами и поиском | PostgreSQL, RabbitMQ, Redis, Memcached; хранилище загрузок | [E2EE мобильных push](https://docs.zulip.com/security/); обычный чат доступен серверу | Настройка продукта; интеграция внешнего провайдера звонков |
| [NATS + JetStream](https://docs.nats.io/learn/core-nats/) | Обмен между сервисами и устойчивые потоки событий | NATS-сервер; дисковое хранение JetStream | TLS / опциональное шифрование хранения; E2EE чатов реализует приложение | Пользователи и устройства, API/ACL чатов, клиентское шифрование, звонки и AI |

Таблица сравнивает назначение и контракты, а не скорость. QGramm объединяет хранение чатов и протокол интеграции; [границы приемки](docs/verification.md) опубликованы отдельно.

### Много чатов, группы и восстановление

Расширенная серия: 2 000 подключений и 1 000 независимых чатов, сообщения 4 КиБ, группы со 100 получателями, reconnect, 10 000 подключений в простое, пятиминутная нагрузка и параллельные файлы. Диапазоны двух повторов на общем M5 Pro / Docker Desktop, квоты 4 CPU / 8 GiB:

| Сервис/профиль | 1 000 чатов, 500/с: доставка p99, мс | 100 получателей × 100/с: доставка p99, мс | RAM при 500/с, МиБ |
|---|---:|---:|---:|
| QGramm, HPKE + SQLite FULL | 4,89–5,56 | 13,43–16,09 | 89–97 |
| NATS 2.15.0, FILE stream/FILE consumers | 9,11–51,99 | 3 960–4 598 | 262–265 |
| Centrifugo 6.9.7, история в памяти | 1,26–1,74 | 3,77–3,79 | 129–170 |

Отдельный контроль NATS: FILE stream/MEMORY consumers дает групповой p99 **3,16–3,28 мс**. Публикации остаются синхронизированными на диск, но гарантии восстановления состояния получателей меняются. Измеритель QGramm не записывает постоянные device receipts. Это разные контракты криптографии, ACK и хранения; универсальный рейтинг протоколов не заявляется. Длительные замеры сохраняют отказы/пропуски; OOM истории Centrifugo 4 КиБ и первоначальная ошибка подключения 10k QGramm отражены в данных. [Методика, p95/p99, все попытки, динамика ресурсов и файлы](docs/scenario-benchmark.ru.md).

### Измеренные задержки и ресурсы

Два повторения на Apple M5 Pro / Docker Desktop Linux arm64, квоты 4 CPU / 8 GiB, 10 000 сокетов и один активный чат. В таблице — диапазоны двух прогонов: доставка в обычной фазе, средний выборочный CPU и выборочный максимум RAM этой фазы. Нагрузка: 100/с 30 секунд, затем 1000/с пять секунд.

| Конфигурация | Доставка p95 / p99, мс | Средний CPU¹ | RAM, MiB |
|---|---:|---:|---:|
| QGramm до оптимизации | 5.31 / 7.34–7.65 | 19.5–20.2% | 583–588 |
| QGramm после, полный ответ | 5.13–5.26 / 7.02–7.26 | 14.3–14.8% | 272–282 |
| QGramm после, компактное подтверждение | 5.19–5.26 / 7.18–7.19 | 13.5–14.1% | 271–272 |
| NATS JetStream, fsync каждой публикации | 4.30–4.97 / 6.52–6.75 | 4.0–4.4% | 459–466 |
| Centrifugo, история в памяти | 3.13–3.54 / 5.18–5.21 | 7.8–8.2% | 425–479 |

¹ 100% — одна CPU. RAM QGramm в обычной фазе снизилась на 52–54%, CPU — примерно на 27%. При всплеске полный ответ дал 83/20 управляемых отказов 503; компактное подтверждение — ни одного. Все принятые сообщения доставлены и сохранены. p99 доставки за весь прогон: 29–71 мс с полным ответом и 7,6–25,4 мс с компактным. Baseline не выполняет HPKE, ACL устройств/чатов и транзакции чата при отправке; история Centrifugo хранится в памяти. Это не максимальная пропускная способность и не сравнение одинакового функционала. [Методика, p95/p99 каждого прогона, профили и сырые данные](docs/performance-dynamics.ru.md). [Предыдущий baseline](docs/comparison-benchmark.md).

Предыдущая серия: при всех 10 000 подписанных сокетах первые три изменения снизили steady CPU на 77%, RAM на 34%; p99 доставки всего прогона — 6,5–7,4 мс. Redis внутри контейнера устойчивого выигрыша не показал и удален. [Два повтора, ограничения и сырые данные](docs/performance-iteration.ru.md).

Предыдущая серия commit/GC/SQL: Redis удален. В диагностике SQL read-helper calls/accepted −27,5%, allocations/accepted −3%; в основных прогонах CPU −2–4%, но p95 слегка вырос и один subscribed burst tail ухудшился. [Полные результаты до/после и ограничения](docs/performance-sql-gc.ru.md).

Эксперимент в dev (в main пока не слит): один запрос истории, ограниченный replay одного события и разбор HPKE-ключа один раз на выдачу. PASSIVE checkpoint включается отдельно; FULL и автоматический checkpoint сохранены. Локальный replay быстрее на8,1%, но итоговый steady p99 выше на8,9%/18,4%. Публикуем регрессию, исправление, диагностику естественного GC и оба профиля нагрузки. [Замеры и ограничения](docs/performance-tail.ru.md).

Следующие три эксперимента (dev): общий commit HTTP batch с опциональным компактным ACK дал ready-batch steady p99−27,2%, CPU−13,3%, RAM+3,4%. Idle-буферы отменены из-за whole-run p99+38,8%; ускорение одиночных сообщений неустойчиво. [Все18 прогонов, контроли и отбор](docs/performance-three.ru.md).

Следующие batch-read эксперименты не дали убедительного выигрыша: общая выдача full-ответа p99+3,8%/CPU+2,8%; предварительные чтения CPU−2,3%, но p99+2,3%. Оба варианта не оставлены; условие для совместного замера не выполнено. [Шесть прогонов и архив экспериментов](docs/performance-batch-reads.ru.md).

## Короткий пример интеграции

```sh
go run ./examples/basic
```

Пример запускает временное loopback-ядро, выпускает Ed25519-токены, создает личный чат, подключается через одноразовый WebSocket ticket, отправляет HPKE-сообщение и расшифровывает событие получателя. Секреты не выводятся. [Разбор кода](docs/integration-example.ru.md) показывает разделение внешнего backend и клиентов.

## Запуск

Минимальный состав — один контейнер, SQLite и volume. PostgreSQL/Redis и медиасервер не нужны. Локальная конфигурация `qgramm.toml` разрешает только loopback-разработку; для контейнера используйте `configs/container.toml` с HTTPS-прокси.

Для нового подключения можно сгенерировать короткую конфигурацию и посмотреть итоговые настройки:

```sh
go run ./cmd/qgramm-build init -preset support -target local -users 1000 -out my-qgramm.toml
go run ./cmd/qgramm-build validate -config my-qgramm.toml
go run ./cmd/qgramm-build explain -config my-qgramm.toml
```

Профили: `minimal`, `support`, `community`, `ai-openai`, `ai-anthropic`. Явные TOML-поля переопределяют профиль, включая отключение модуля через `false`. `explain` показывает значения, их происхождение, вычисленные лимиты и имена переменных с секретами; значения секретов не читает. Это проверка конфигурации; при запуске отдельно проверяются секреты и состав бинарника. Подробности — в [русском справочнике](docs/reference.ru.md).

```sh
go run ./cmd/qgramm-build plan -config qgramm.toml
go run ./cmd/qgramm-build build -config qgramm.toml -out bin/qgramm
```

В TOML хранятся настройки и имена переменных с секретами. Значения ключей передаются через окружение при запуске. Состав функций выбирается при сборке: выключенные модули исключаются из бинарника; изменение состава требует пересборки.

```sh
go run ./cmd/qgramm-build compose -config configs/container.toml -out compose.yaml
docker compose --env-file .env up -d --build
```

Внешний backend управляет пользователями, ключами устройств, чатами и правами, выдает короткие Ed25519-токены. Core сохраняет сообщения и события транзакционно, восстанавливает доставку после reconnect и различает принятие, доставку устройству и прочтение.

Доступны отдельные модули групп, файлов, операций над сообщениями, WebRTC-сигналинга, MLS E2EE, OpenAI/Anthropic и MCP/HTTP-инструментов. Для звонков нужен внешний TURN. AI — доверенный получатель внутри контейнера: провайдер получает содержимое его чата.

`expected_concurrent_users` задает ожидаемое число подключенных пользователей. CLI рассчитывает внутренние лимиты и генерирует Compose с оценкой ресурсов. Пока расчет некалиброванный; это не обещание производительности.
