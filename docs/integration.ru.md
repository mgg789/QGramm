# Подключение к своему backend

1. Настройте HTTPS, persistent volume и секреты окружения по именам из TOML. Публичный Ed25519-ключ проверки JWT — base64 32 байта; master и HPKE — отдельные случайные base64 32-байтные ключи; management secret — минимум 32 символа.
2. Ваш backend вызывает management API: создает пользователя, устройство с X25519 public key и Ed25519 signing key, затем личный или групповой чат.
3. Backend подписывает короткий JWT с `iss`, `aud`, `sub`, `device_id`, `iat`, `exp`; срок не более 15 минут. Management secret клиентам не передается.
4. Клиент проверяет привязанный вашим backend публичный ключ контейнера, шифрует basic-сообщение HPKE и отправляет с уникальным `operation_id`. Для E2EE клиент самостоятельно реализует MLS suite1 и хранит ключи.
5. Для realtime клиент получает одноразовый ticket через HTTP, подключает WebSocket и подписывается с последним сохраненным cursor. Подтверждения доставки/прочтения отправляет явно через HTTP.

Повторяйте исходный запрос с тем же ID, не создавая новый ciphertext для повтора. Измененное содержимое с прежним ID вызывает конфликт. В батчах повторяются только неуспешные элементы. При истечении срока replay требуется синхронизация истории и состояния.

Для отправки и батчей можно передать `Prefer: return=minimal`. После устойчивого
commit одиночный запрос возвращает 201 и
`{"status":"accepted","receipt":{"message_id":"...","chat_id":"...","operation_id":"...","seq":1}}`.
Успешные элементы батча содержат `receipt` вместо `message`; ошибки сохраняют
прежний формат. Сервер добавляет `Preference-Applied: return=minimal`.
Без заголовка сохраняется полный ответ с сообщением. Компактный ответ исключает
повторное чтение и шифрование содержимого для отправителя; доставка и шифрование
для получателя сохраняются. При точном повторе возвращается идентификатор исходного
приёма, включая случай последующего редактирования или удаления, с повторной
проверкой текущего доступа. Это подтверждение приёма, а не доставки или прочтения.

Replay сохраняет порядок событий чата, но события сообщений содержат текущее
доступное состояние сообщения. Чтение журнала, пакетная проекция сообщений и
опциональные обработчики проекции выполняются отдельными запросами; страница не
является единым снимком БД. После удаления прежнее событие создания может уже
содержать tombstone. Клиент учитывает revision и приоритет удаления; изменение
участия во время проекции может потребовать повторной синхронизации.

По умолчанию участник видит историю с момента входа. `history=all` разрешает внешнему backend явно выдать старую историю; для E2EE нужны ключи или перенос истории со старого устройства, сервер их не создает.

Глобальное удаление убирает активный payload и отправляет tombstone; `author_only` скрывает только у автора. Скачанные получателями копии удалить гарантированно нельзя. Редактирование требует ожидаемой revision; реакции передаются числовыми типами словаря TOML.

Шифрование basic не защищает от администратора контейнера. Human E2EE требует проверки идентичностей клиентами. AI-чат раскрывает содержимое выбранному провайдеру и разрешенным инструментам. Автовосстановление старого MLS-state из backup опасно повторным использованием счетчиков.

Точные HTTP/WS поля, AAD и примеры находятся в [нормативном руководстве](integration.md), [OpenAPI](openapi.json) и профильных документах. Клиентский UI/SDK не поставляется.
