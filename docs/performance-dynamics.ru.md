# Изменения производительности, 2026-10-04

[English](performance-dynamics.md). Это повторные измерения на одном Mac и
Docker Desktop, а не квалификация выделенного Linux-сервера с SSD.

## Что изменено

Исходный core: `658346e`; оптимизированный core: `31d31b2`.

1. Добавлена отдельная сборка для CPU/heap/block/mutex-профилей и статистики
   пулов SQL. У обычного контейнера нет profiling/debug HTTP endpoints.
2. Убраны ежесекундные таймеры у неподписанных сокетов и индивидуальные SQL-проверки
   устройств: проверки объединены, уведомления о событиях объединяются.
   HTTP-обработчик после upgrade возвращается; сокет живёт под управлением core.
   Это освобождает стек HTTP-обработчика и его буферы. Отзыв доступа и replay
   сохраняются; периодическая проверка доступа дополняет прямое отключение.
3. Выдача сообщений использует пакетную проекцию. Опциональный
   `Prefer: return=minimal` возвращает устойчивое подтверждение с ID/seq, без
   повторного чтения и шифрования содержимого для отправителя. Ответ по
   умолчанию остаётся полным; варианты измерены отдельно.
4. SQLite WAL использует ограниченный read pool и отдельное соединение для
   записи. `synchronous=FULL`, атомарность message/event/idempotency и проверки
   ACL внутри транзакции сохранены.

## Методика

- Apple M5 Pro, macOS 26.6.2; Linux arm64 VM Docker Desktop, 4 CPU и 8 GiB
  ограничений на контейнер, генераторы снаружи контейнеров.
- 10 000 разных пользователей/сокетов, одна активная личная беседа,
  остальные подключения простаивают. 17 байт plaintext до шифрования.
- После подключения — 10 секунд idle, 30 секунд по 100 сообщений/с и
  5 секунд по 1000 сообщений/с. Между успешными нагрузочными прогонами
  оставлено минимум 60 секунд для восстановления состояния сокетов хоста.
- QGramm до/после использует один и тот же Go 1.26.8 и минимальный профиль;
  фиксированы image ID, server binary SHA256 и исходный commit в JSON.
  Генератор — Go 1.26.4. Профили отдельно собраны Go 1.26.4 в обоих вариантах.
- Перцентили — nearest rank по успешным запросам. ACK означает устойчивое
  принятие; delivery означает получение события тестовым получателем.
  Проверяется также число сообщений в сохранённой истории.
- Docker stats примерно раз в 2 секунды помечены фазами. В таблице CPU idle
  указан медианный отсчёт, CPU steady — среднее отсчётов. 100% — один CPU.
  RAM — максимум выборки внутри соответствующей фазы, не точный пик RSS.
  Всплеск даёт лишь 2–3 отсчёта CPU и не позволяет уверенно оценить среднее.
- Первый отсчёт новой фазы может включать предыдущую фазу. В after/round2
  один idle-отсчёт 46.1% включает setup; он остаётся в исходном JSON. Поэтому
  для idle применяется медиана во всех системах. Helper также показывает
  среднее с исключением первого отсчёта каждой фазы для всех систем.
- Прогоны последовательные, без рандомизации порядка и доверительных
  интервалов. Два повторения показывают разброс; это не универсальный рейтинг.
  TLS, активные 10 000 отправителей, большой fan-out и большой файл не измерены.

## Два повторения: исходный и оптимизированный QGramm

Steady — только фаза 100 сообщений/с. Последний столбец — p99 доставки
**всего** прогона, включая всплеск, а не p99 отдельной burst-фазы.

| Вариант / повтор | ACK steady p95/p99, мс | Delivery steady p95/p99, мс | CPU idle медиана | CPU steady среднее | RAM steady/burst, MiB | 503 | Delivery всего p99, мс |
|---|---:|---:|---:|---:|---:|---:|---:|
| До / 1 | 5.098 / 7.479 | 5.309 / 7.654 | 9.32% | 20.204% | 583.0 / 664.9 | 0 | 71.491 |
| После, полный ответ / 1 | 5.159 / 6.757 | 5.260 / 7.021 | 0.08% | 14.767% | 282.4 / 284.0 | 83 | 71.159 |
| После, receipt / 1 | 4.793 / 6.949 | 5.262 / 7.178 | 0.07% | 14.094% | 271.3 / 275.6 | 0 | 7.621 |
| До / 2 | 5.080 / 7.180 | 5.309 / 7.341 | 10.84% | 19.533% | 587.6 / 665.2 | 0 | 25.275 |
| После, полный ответ / 2 | 4.968 / 7.162 | 5.128 / 7.257 | 0.11% | 14.252% | 271.9 / 281.1 | 20 | 29.157 |
| После, receipt / 2 | 4.862 / 6.763 | 5.192 / 7.193 | 0.07% | 13.542% | 271.4 / 274.5 | 0 | 25.412 |

Полный ответ: RAM steady уменьшилась на **51.6% / 53.7%**, RAM burst — на
**57.3% / 57.7%**, средний CPU steady — на **26.9% / 27.0%** в соответствующих
повторениях. Медиана idle CPU уменьшилась примерно на 99%.

Задержки steady близки. Общий p99 не улучшился устойчиво: во втором повторении
полного ответа он вырос с 25.275 до 29.157 мс. Появился управляемый backpressure
во время всплеска: 83 и 20 отказов. Во втором повторении код причины подтверждён
как `request capacity reached`; причина первого не записана. Все принятые
сообщения доставлены и найдены в истории: 7993/7990 до, 7901/7965 после с полным
ответом, 7982/7993 с receipt. Потерь принятых сообщений и неожиданных disconnect
не обнаружено. 503 здесь не ретраились; они считаются отдельно от successful
latency. Генератор QGramm иногда не выдаёт все номинальные 8000 операций из-за
тикера; это отражено в `offered`, а не трактуется как потеря доставки.

Receipt устранил backpressure в обоих повторениях. По сравнению с полным
ответом after p99 всего прогона улучшился на 89.3% / 12.8%. По сравнению с
исходным core во втором повторении p99 практически тот же: 25.412 против
25.275 мс. Это не обещание одинакового улучшения хвоста при любой нагрузке.

## Два повторения с альтернативами

Ниже диапазоны между двумя прогонами, а не объединённые или усреднённые
перцентили. CPU steady рассчитан по 14–15 отсчётам каждого прогона; JSON
сохраняет все отсчёты и показатели отдельных фаз. В каждом прогоне альтернатив
приняты и доставлены все 8000 операций, ошибок publish/receive и дубликатов нет.

| Система / режим | ACK steady p95, мс | ACK steady p99, мс | Delivery steady p95, мс | Delivery steady p99, мс | Средний CPU steady | Максимум выборки RAM steady, MiB |
|---|---:|---:|---:|---:|---:|---:|
| QGramm до | 5.080–5.098 | 7.180–7.479 | 5.309–5.309 | 7.341–7.654 | 19.533–20.204% | 583.0–587.6 |
| QGramm после/full | 4.968–5.159 | 6.757–7.162 | 5.128–5.260 | 7.021–7.257 | 14.252–14.767% | 271.9–282.4 |
| QGramm после/receipt | 4.793–4.862 | 6.763–6.949 | 5.192–5.262 | 7.178–7.193 | 13.542–14.094% | 271.3–271.4 |
| NATS 2.11.3 JetStream, always fsync | 4.263–4.889 | 6.524–6.712 | 4.299–4.971 | 6.523–6.746 | 3.994–4.399% | 458.6–465.9 |
| Centrifugo 6.2.3 memory history | 3.146–3.520 | 5.064–5.211 | 3.131–3.544 | 5.184–5.211 | 7.789–8.152% | 424.6–479.4 |

QGramm теперь потребляет меньше RAM в этом сценарии, но всё ещё больше CPU,
а задержка steady выше. Пути обработки различаются: QGramm проверяет
Ed25519-идентичность/ACL, идемпотентность, chat/event-транзакции и HPKE.
Его latency включает HPKE/выпуск токена на хосте и HTTP-публикацию. NATS
использует общий connection token, plaintext WebSocket, файловый stream,
explicit consumer ACK, replicas=1, `sync_interval=always`. Centrifugo использует
connection HS256 JWT и ограниченную историю в памяти без durable chat storage.
TLS отсутствует во всех изолированных стендах. Это сравнение разных готовых
путей обработки, а не протоколов с одинаковой безопасностью и функциональностью.

## Что показали профили

Профили содержат принудительный GC и сериализацию больших стеков; их latency
исключена из таблицы. Сводки: [до](benchmarks/perf-profile-before-summary.json),
[после](benchmarks/perf-profile-after-summary.json).

| После подключения 10 000 сокетов, forced GC | До | После |
|---|---:|---:|
| Живая Go heap, MiB | 190.14 | 67.16 |
| Память стеков, MiB | 196.62 | 79.09 |
| Goroutines | 20 024 | 20 026 |
| Суммарное SQL-ожидание writer после setup до позднего load-снимка | 50.97 с | 6.67 с |
| Число SQL-ожиданий writer в этом интервале | 52 837 | 2 234 |

Heap уменьшилась на 64.7%, стеки — на 59.8%. Число goroutines почти не изменилось;
освободились удерживаемые HTTP-стеки/буферы. Сумма SQL wait — время всех ожидающих
goroutines, которое может превышать wall-clock. В новых reader pool отмечены
только 8 ожиданий; добавление reader workers не выглядит первым приоритетом.

Во всём CPU-профиле после изменений SQL VM занимает 21.3% cumulative, разбор SQL
14.1% cumulative. Это пересекающиеся стеки, их нельзя складывать. Профиль также
содержит setup. В отфильтрованном пути `sendMessage` SQL parser `_yy_reduce`
занимает 0.88 CPU-с, SQL VM — 1.24 CPU-с, системные вызовы — 1.08 CPU-с.
Остались криптографические вычисления HPKE; профиль не подтверждает объяснение
«всё отставание вызвано криптографией».

## Следующие изменения

1. Подготовленные SQL-запросы для горячих путей: измерить уменьшение parse/VM
   CPU и allocations, сохранив текущую транзакцию и ACL.
2. Разобрать burst-admission: длительность ожидания writer, fsync, GC и занятые
   HTTP slots в обычной сборке. Затем экспериментировать с ограниченной очередью
   записи или небольшими группами commit; ACK выдавать только после durable commit.
   Повышать лимит in-flight без измерения нельзя: это может только увеличить p99.
3. Объединить fallback replay для подписанных сокетов: там пока остаётся
   ежесекундный таймер. Проверить доставку при переполнении wake-очереди и
   fairness, затем измерить много одновременно активных подписок.
4. Дополнительный профиль активных чатов и группового fan-out, длительный soak
   и целевой Linux/SSD. Настройка на 10 000 преимущественно idle сокетов не
   доказывает скорость при 10 000 активных отправителей.
