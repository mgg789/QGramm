# Следующие три оптимизации и Redis — 2026-10-04

[English](performance-iteration.md).

## Реализованные изменения

1. SQL-запросы горячего пути используют ограниченный кэш prepared statements:
   до128 форм на каждый пул. Запросы транзакции подготавливаются до захвата
   единственного write-соединения; неизвестная форма внутри транзакции идет
   напрямую через нее, без ожидания собственного занятого pool.
   modernc1.38.2 разбирал SQL заново даже для `sql.Stmt`; переход на1.46.1
   с согласованным libc1.67.6 включает повторное использование native statement.
   [Исходный код драйвера](https://gitlab.com/cznic/sqlite/-/blob/v1.46.1/stmt.go).
2. Ограниченная очередь записи сохраняет отдельный FULL commit для каждого
   сообщения, повторную проверку ACL/epoch/idempotency внутри транзакции и
   однозначный результат при отмене. Проекция ответа выполняется вне writer.
   Предел одновременно работающих HTTP-запросов сохранен; добавлена ограниченная
   очередь ожидания до100мс перед отказом с Retry-After. Метрики очереди,
   service/commit и admission доступны только приватной benchmark-сборке.
3. Общий цикл раз в секунду читает heads подписанных чатов пакетами по500.
   Каждый подписанный сокет больше не выполняет собственный пустой replay.
   Измененный/новый/исчезнувший head пробуждает получателей. Reconnect сразу
   восстанавливает свой cursor; события проверяют ACL, management revoke
   немедленно отключает доступ, потерянный wake восстанавливается из SQLite.

Коммиты: `9cf77c2` — три изменения, `f4d4fd5` — Redis-модуль,
`2871485` — пустое окружение дочернего Redis. Group commit и ACK до устойчивого
сохранения не добавлялись. [Redis](redis.ru.md) — опциональный Pub/Sub-брокер
уведомлений в том же контейнере. Он добавляет IPC перед fan-out и сохраняет
прежний локальный fallback и независимый SQLite replay раз в секунду.
Сообщения и идемпотентность остаются в SQLite.

## Методика

- Apple M5 Pro/macOS26.6.2, Docker Desktop Linuxarm64, kernel6.12.76-linuxkit.
  Для каждого сервера запрошена одна квота4CPU/8GiB. Отображаемый Docker
  эффективный предел памяти — около7.748GiB. Это общий хост, не выделенный
  Linux/SSD-стенд; посторонние контейнеры не изменялись.
- По два повтора каждого из двух профилей для каждого варианта:10000 сокетов,
  10 секунд idle,100 сообщений/с30 секунд и1000/с5 секунд; cooldown минимум60с.
  Basic HPKE, полный ответ, синтетический plaintext17 байт; TLS не измеряется.
  Host-generator и runner зафиксированы; server Go1.26.8 одинаков.
- Standard: один активный личный чат, один подписанный получатель,9999 сокетов
  без подписок. Subscribed:5000 личных чатов,10000 команд подписки,4999 пустых
  неактивных чатов. В активном чате подписаны и отправитель, и получатель;
  метрика доставки относится к выбранному получателю. Отправитель также
  получает события, поэтому активный fan-out в этом профиле чуть больше.
- Redis и Go находятся в общей квоте. Docker stats включает оба процесса;
  версия и список процессов записаны. Redis получает пустое окружение и только
  ID чата в уведомлениях, без нового внешнего сервиса.
- p95/p99 nearest-rank считаются по успешным запросам отдельно для обычной фазы
  и всего прогона. Их нельзя смешивать: доля успешных burst-запросов меняет
  общий percentile. Отказы публикуются отдельно. Delivery — приход события
  `message.created`, а не расшифровка/устойчивый device ACK. Генератор сравнивает
  количества events/history, не набор каждого received message ID. Расшифровка,
  точный retry, cursors/ACK и replay проверяются отдельными интеграционными тестами.
- CPU — среднее фазовых Docker samples примерно раз в2с;100% — одно ядро.
  Idle CPU — медиана, чтобы уменьшить влияние границы setup/idle. RAM — максимум
  выборки внутри фазы, не точный RSS/пик. Публикуются оба повтора.
- Один успешный baseline-прогон пересекся с инспекционными тестами. Его JSON
  сохранен с причиной исключения и заменен новым прогоном; в таблицы он не входит.
  Инструментированные профили не используются для сравнения задержек.

### Что изменилось

- При всех подписанных сокетах: среднее двух CPU mean снизилось на **77,3%**, среднее двух RAM max — на **34,1%**. Медианы idle CPU: **82,53/82,88% → 1,83/1,90%** (−97,7% по их средним). Общий p99: **70,37/85,77 → 6,51/7,43 мс** (−91,1% по средним per-run p99). Отказы 47/161 → 0/0.
- Это выигрыш по ресурсам и хвосту смешанного прогона, а не ускорение каждого запроса: средние steady p95/p99 выросли на 7,7%/19,6%. Двух повторов недостаточно для статистической значимости; изменение доли успешных burst-запросов влияет на общий p99.
- Standard: CPU снизился примерно на 5,7%; память и steady latency близки. Один optimized repeat имеет худший общий p99 14,55 мс, поэтому общего улучшения всех задержек здесь нет.
- Redis: standard CPU вырос на **8,9%** относительно первых трех. В subscribed CPU −3,1%, RAM +2,2% по средним двух повторов; такой небольшой эффект не отделен от шума. Общий p99 37,97/6,99 мс против 6,51/7,43 мс без Redis — устойчивого выигрыша нет.

**По умолчанию оставляем SQLite + локальные уведомления.** Redis доступен как явно включаемый эксперимент. Здесь проверен Pub/Sub wake broker внутри одного контейнера; результаты не распространяются на другие схемы использования Redis.

### Что менять дальше

1. Проверять writer wait/service/commit и GC на более длительном прогоне; искать источник хвостов до изменения размера очередей.
2. Измерить и сократить повторные ACL/projection SQL-чтения без изменения проверки доступа и атомарности.
3. Проверить распределенную активность по чатам, fan-out и длительный soak; затем повторить на выделенном Linux/SSD. Эта серия не калибрует production sizing.

## Диагностика очереди записи

Отдельный инструментированный прогон: **2 000 подписанных пользователей / 1 000 чатов**, та же нагрузка 100/с + 1 000/с. 7 991 accepted = events = history; ошибок commit, отмен и отказов очереди нет. Средние: ожидание writer **0,491 мс**, обслуживание **0,725 мс**, commit **0,626 мс**. Commit занимает **86,4% времени обслуживания writer**, а не общей задержки сообщения. Это время SQLite commit/driver, не отдельное измерение fsync.

HTTP admission не ожидал слотов; прирост writer DB pool waits во время трафика — 0. Очередь writer имела предел 32. Эти счетчики не дают p95/p99 очереди; профилирование и принудительный GC меняют timing, поэтому этот прогон исключен из сравнения 10 000 пользователей. Следующий полезный шаг — фазовые распределения commit/queue wait и корреляция хвостов с GC и диском, а не увеличение очереди без измерения.

## Артефакты и воспроизведение

JSON фиксирует image IDs, server binary SHA256, Go и immutable source snapshot
SHA. Archive/overlay отличается от окончательного exact Git tree, например
неиспользуемыми файлами generator/Go sums. Коммиты выше обозначают реализацию,
а не выдают снимок за точную сборку этого commit. Native image получил только
лицензионный слой; его бинарник не изменился. Redis пересобран после Env fix
до основных Redis-замеров; Linux `/proc/<Redis PID>/environ` имеет0 байт.

```sh
go build -o work/qgramm-bench ./cmd/qgramm-bench
# Отдельно соберите сравниваемые images из нужных revisions/profiles.
python3 tools/benchmark.py --image qgramm:minimal --out work/standard.json \
  --generator-binary work/qgramm-bench
python3 tools/benchmark.py --image qgramm:minimal --out work/subscribed.json \
  --generator-binary work/qgramm-bench --idle-subscriptions
python3 tools/benchmark.py --image qgramm:redis --redis --out work/redis.json \
  --generator-binary work/qgramm-bench --idle-subscriptions
```

Generator executable должен быть одинаковым; images/config фиксированы;
запуски последовательны с cooldown. Secret fixtures находятся вне image/отчета.
Это сравнение конкретных вариантов, не максимальная пропускная способность,
калибровка production-ресурсов, криптоаудит или оценка всех способов применения Redis.
