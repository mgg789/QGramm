# SQL выдачи и необязательный checkpoint WAL

[English](performance-tail.md).

## Что изменилось

Коммит `0257fd2`, затем `bc73c00` сохраняет транзакцию message/event/operation и `synchronous=FULL`. История читает актуальные ACL, статус пользователя/устройства, ключ получателя и упорядоченную страницу **одним** SQL-вызовом вместо трех. Непустой replay событий — **двумя** вместо трех; пустой — одним. HTTP-аутентификация и optional hooks добавляют свои чтения. Повторные ссылки на сообщение внутри страницы получают один payload и один вызов проекции/hook; ранжирование ограничено страницей до 200 событий. SQL rows закрываются до криптографии и hooks.

Публичный ключ получателя разбирается один раз на пакет проекции. Каждый HPKE-конверт сохраняет отдельные sender/setup/encapsulation и прежнюю привязку к идентичности/чату/операции. Между запросами ACL и ключи не кешируются.

По умолчанию `storage.checkpoint_interval_ms=0`, дополнительный worker/пул отсутствуют. Эксперимент: интервал 100 мс, `wal_checkpoint_bytes=1048576`. Отдельное writable-соединение выполняет `PASSIVE`, сохраняет FULL и автоматический checkpoint SQLite, пропускает неизменившийся полностью обработанный WAL, повторяет неполные/busy/ошибочные попытки. Порог — условие запуска, а не ограничение дискового пространства. Длительный reader может задерживать обработку WAL; I/O checkpoint может конкурировать с commit. [Конфигурация](configuration.md), [SQLite WAL](https://www.sqlite.org/wal.html).

## Методика

Исходный вариант — точный минимальный образ предыдущего `b131b63`; новый — неизменяемый архив `0257fd2`. Go 1.26.8, один замороженный генератор. Три варианта: исходный, SQL без фонового checkpoint, SQL с checkpoint. Каждый — два повтора standard/subscribed, всего 12 основных измерений последовательно с паузой 60 с. Первые две исходные попытки пересеклись с проверками исходников на хосте: их исключили и повторили после основной серии. Всего 14 попыток, 12 включенных результатов. Сборки и проверки не запускаются одновременно с включенными измерениями; сторонние сервисы общего хоста остаются ограничением.

Нагрузка прежняя: 10 000 WebSocket, 10 с idle, 100 сообщений/с 30 с, затем 1000/с 5 с; HPKE, 17 байт текста, полный HTTP-ответ. Standard — один подписанный получатель. Subscribed — 5000 личных чатов/10 000 подписок, один активный чат с двумя подписанными сторонами. Отложенная проверка устойчивого насыщения writer не добавляется.

Apple M5 Pro, 18 логических CPU хоста, macOS 26.6.2, Docker Desktop Linux arm64 VM. Квоты контейнера 4 CPU/8 GiB; генератор на хосте. SQLite в Docker volume; выделенного Linux/SSD нет. TLS не измеряется.

p95/p99 — nearest rank успешных запросов каждого прогона; среднее перцентилей прогонов не является общим перцентилем. CPU — среднее фазовых samples Docker stats (100% = одно ядро); RAM — максимум samples, не точный пик RSS. Два повтора не дают доверительного интервала. Сравнение accepted/events/history проверяет числа, но не точные множества ID, расшифровку и persistent receipts; эти контракты покрыты отдельными тестами.

## Первый вариант и исправление

[Первую серию из 12 прогонов](benchmarks/tail-summary.json) сохраняем целиком: уменьшение SQL-чтений сопровождалось регрессией steady p99 на14,2% (standard)/7,8% (subscribed), CPU на4,3%/12,2%. По этим результатам вариант не переносился в main. Checkpoint относительно первого SQL-варианта изменил p99 на−6,9%/+3,8%, без устойчивого выигрыша CPU. По умолчанию он остается выключенным.

В `bc73c00` обычная выдача одного события обходит оконное ранжирование. Ограниченный диапазон возвращает ближайшее доступное событие до наблюдавшегося head; конкурентный append доставляется следующим replay/Wake. Для backlog остается ранжирование страницы до200 событий. ACL, устройства, ключи и tombstone проверяются свежими.

Локальный microbenchmark: один сохраненный HPKE message,100 warmup и10000 вызовов Events,3 повтора каждого варианта, без HTTP и записи внутри измеряемого цикла, естественный GC. Native Go1.26.4/macOS отличается от Docker Go1.26.8 основных замеров. [Сырые значения и hash одинакового приватного fixture](benchmarks/tail-replay-cost.json).

| Replay | Среднее, мкс | Байт/вызов | Allocations/вызов |
|---|---:|---:|---:|
| Прежний SQL | 58,88 | 16416 | 255,05 |
| Первый ranked SQL (`0257fd2`) | 108,29 | 15647 | 235,05 |
| Range для одного события (`bc73c00`) | 54,10 | 15647 | 235,05 |

Итог microbenchmark относительно прежнего: время−8,1%, выделенные байты−4,7%, число выделений−7,8%. Это не задержка API и не максимальная пропускная способность. Разбор ключа один раз на batch отдельно экономит304 байта/5 allocations на каждый envelope после первого; диапазоны времени пересекаются, ускорение HPKE не заявляем.

## Диагностика

Отдельные subscribed-прогоны с 10 000 пользователями используют тот же генератор и приватную сборку `qg_bench_profile` в режиме timeline-only. Каждые 100 мс записываются SQL query lifetime, queue/body/commit/service/projection/WS, естественные GC-паузы и размер WAL. Принудительного GC и CPU/block/mutex-профилировщиков нет. Наблюдатель сам меняет расходы; его задержки не входят в основное сравнение.

Диагностический исходный образ — `27cc7e5` с одинаковой обвязкой диагностики/checkpoint, но выключенным worker и прежними SQL/HPKE. Единственная правка messages.go — таймер вокруг прежнего цикла проекции после закрытия SQL rows. Хэши исходников, образа, бинарника и runner записаны в JSON; оба диагностических образа дополнительно получают одинаковую обвязку signal-marked snapshots для выравнивания часов.

Кольцо хранит последние 64 записи стадий от 8 мс и все попытки фонового checkpoint. Скрипт отмечает обнаруженную потерю записей между samples. Фазы наблюдаются на хосте через файл замороженного генератора каждые 100 мс. До и после прогона снимаются по три пары timestamp хоста/контейнера через signal-marked snapshot; выбирается пара с минимальной неопределенностью на каждой стороне. Границы фаз переводятся в часы контейнера. Неопределенность или наблюдаемый дрейф смещения свыше 100 мс отклоняют обработку. SQL lifetime включает подготовку, ожидание пула и потребление до Scan/Close; прямые SQL-вызовы вне helpers не учтены. Стадии пересекаются, их нельзя складывать. Автоматический checkpoint внутри commit отдельно не выделен. Совпадение с GC по времени не доказывает причину, GC assist и задержки планировщика напрямую не измеряются. Raw timelines остаются приватными; публикуются агрегаты.

Эти три диагностических прогона относятся к **первому ranked-варианту**, а не к последующему range-исправлению. [До](benchmarks/tail-before-timeline-summary.json), [SQL](benchmarks/tail-sql-timeline-summary.json), [SQL + checkpoint](benchmarks/tail-checkpoint-timeline-summary.json).

| Счетчики измеряемого интервала | До | Ranked SQL | Ranked SQL + checkpoint |
|---|---:|---:|---:|
| Committed messages интервала | 7961 | 7965 | 7991 |
| Read-helper calls | 77019 | 61148 | 62814 |
| Выделено, MiB | 684,5 | 665,7 | 682,6 |
| Естественные GC cycles | 9 | 9 | 10 |
| Суммарная GC pause, мс | 5,39 | 5,75 | 6,18 |
| Наибольшая записанная GC pause, мс | 1,75 | 1,88 | 1,50 |
| Наибольший sampled WAL, MiB | 4,32 | 4,05 | 4,47 |

Прежний subscribed whole p99 31,994мс в свежих контролях не воспроизвелся. В одном ranked diagnostic были6 commit от8мс, максимум55,44мс, без временного пересечения с записанными stop-the-world GC паузами. В before/checkpoint таких commit не было. Это не доказывает причину fsync/checkpoint: ожидание планировщика/I/O и автоматический checkpoint не разделены. Фоновый worker сделал351 попытку, среднее2,20мс/максимум4,62мс, ошибок не зарегистрировано. Физический размер WAL устойчиво не сократился; PASSIVE его не обрезает. Потери записей между snapshots не обнаружено. Настройки GC не менялись.

## Воспроизведение

[Команды EN](performance-tail.md#reproduction). Для варианта checkpoint добавить `--checkpoint-interval-ms 100 --checkpoint-bytes 1048576`. Для отдельной диагностики собрать минимальный server с `-tags=qg_bench_profile`, добавить `--profile-dir work/private-timeline --timeline-only`, затем обработать timeline скриптом `tools/performance/timeline.py`. Основные измерения запускать без этих диагностических флагов.

## Проверки

Прошли минимальный/полный (13 features) `go test -race`, profile-tag race, `go vet ./...`, пример Ed25519/WS/HPKE/receipt и матрица 28 сборок/7 ошибочных конфигураций. Независимые ревью и инспекция прошли перед коммитом кода. Регрессии проверяют пустую историю, порядок/лимиты/вступление, актуальные ACL/устройства/ключи, tombstone/hook-once/cross-chat denial, независимые HPKE encapsulations, FULL/autocheckpoint/zero busy timeout после reconnect, pinned readers, активный writer, остановку worker и отсутствие дополнительных ресурсов при его отключении.
